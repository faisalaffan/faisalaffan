### エンジニアリングに対する考え方

- **マルチテナンシーは設計上の判断であり、機能フラグではない。**
  テナント分離、RBACスコープ、コストセンターモデリングは、
  スキーマに後付けするのではなく、最初から設計に組み込む必要があります。
  両方の側面を経験してきました — まずBTPN Syariahのバンキングプラットフォーム（410万人のユーザーを抱える）に
  マルチテナンシーを後付けで導入し、その後MSTOREとPAYSALESをゼロから
  マルチテナンシーを第一級の制約として構築しました。
  その違いは歴然です。シングルテナントのコードベースへの後付けは、
  多くのSaaS製品が静かに息絶える原因です — だいたい3社目のエンタープライズ顧客が
  「テナントをもう一つ追加できますか？」と尋ねたとき、スキーマがそれを拒否します。
  早い段階で正しく設計するのは時間がかかります。
  しかし、間違った設計は何年もかけて代償を払うことになります。

- **契約（Contract）が設計のズレを防ぐ — 特にAIエージェント相手には。**
  APIスペック、DBスキーマ、サービス境界がソース・オブ・トゥルースです。
  それ以外はすべて実装の詳細です。これはBTPNでMLインフラを構築する中で
  苦い経験から学びました。OJK（インドネシア金融サービス機構）への準拠のため、
  すべての与信スコアリング予測が完全に再現可能でなければなりませんでした —
  誰がリクエストしたか、いつ、どのような入力で、何が出力されたか。
  同様に、RAGパイプラインを構築する際も、モデル自体と同様に
  バックエンド契約が重要でした。LLMはコードを高速に生成しますが、
  不変条件を正確に守ることはしません — だからこそ、契約駆動のワークフローが
  今、より重要になっているのです。

- **観測可能でなければ、出荷したことにならない。**
  LGTMスタック — Loki、Grafana、Tempo、VictoriaMetrics — は
  私が所有するすべてのプロジェクトの基本構成です。
  しかし本当の教訓は、鉱業向けに構築した燃料異常検知システムから得ました：
  純粋なセンサーデータでは盗難パターンを捉えられませんでした。
  GPS移動テレメトリーと燃料データの組み合わせによって初めて
  異常が可視化されたのです。初月に3件の盗難を検出、
  年間燃料コストを8〜12%削減しました。ここから得た教訓：
  観測可能性とは単なるダッシュボードではありません —
  どのシグナルが実際に意味を持つかを理解し、
  互いに連携するよう設計されていないレイヤー間で相関させることです。

- **最悪のシナリオを想定して構築せよ。**
  これまで経験した最も困難なエンジニアリングの問題にはすべて共通のパターンがあります：
  通常の状態ではシステムは正常に動作していました。
  しかし、遠隔鉱山サイトへのVSATリンクが512kbpsに低下したとき —
  または自己交差するポリゴンが下流のすべての空間クエリを
  静かに破壊したとき — あるいはデッドゾーンにいる現場エージェントが
  ローン支払いデータを失うことなくオフライン同期を必要としたとき。
  BTPNではオフライン・ファーストのアーキテクチャで
  データ損失を23%からゼロに削減しました。Petroseaでは
  毎秒50,000件の空間イベントに対して2秒未満で動作する
  ジオフェンス侵入検知を構築しました。ハッピーパス設計は簡単です。
  エッジケースこそが、システムの存在価値を証明するものです。

- **AI支援型であれ、AI依存型になるな。**
  Claude Code、MCPサーバー、セマンティック検索は力の増幅器です —
  積極的に活用しています。しかし、すべての差分を読み、
  すべてのデプロイに責任を持ち、出荷するすべての行に自信を持っています。
  レバレッジは移転できますが、説明責任は移転できません。
  ツールは実行を加速しますが、なぜその設計判断が下されたかを
  理解することに代わりはありません。インシデント発生時に
  午後11時、別のエンジニアにトレードオフを説明できなければ、
  それを出荷すべきではなかったのです。
