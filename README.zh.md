### 我对工程的理解

- **多租户是一种设计决策，不是一个功能开关。**
  租户隔离、RBAC范围、成本中心建模必须
  在数据库模式设计时就考虑到，而不是事后打补丁。
  这两方面我都亲身经历过 — 先是在服务410万用户的BTPN Syariah银行平台
  中为已有系统打上多租户补丁，然后从零开始构建MSTORE和PAYSALES，
  将多租户作为一等约束条件来设计。
  区别是天壤之别。在单租户代码库中打多租户补丁，
  是大多数SaaS产品悄然消亡的原因 — 通常发生在第三个企业客户
  问"能不能再加一个租户？"而数据库模式说"不行"的时候。
  早期做对设计，代价是设计时间。
  做错了，代价是几年时间。

- **契约（Contract）防止设计漂移 — 尤其是与AI Agent合作时。**
  API规范、数据库模式、服务边界是唯一的事实来源。
  其他一切都是实现细节。这一点是我在BTPN构建ML基础设施时
  通过惨痛教训学到的：OJK（印尼金融服务监管局）合规要求
  每个信用评分预测都必须可完整追溯 —
  谁请求的、什么时间、什么输入、输出了什么。
  后来构建RAG管道时也是一样，后端契约和模型本身同等重要。
  LLM写代码很快，但它们不会遵守任何不变量 —
  正因如此，契约驱动的工作流现在比以往任何时候都更重要。

- **不可观测，就是未交付。**
  LGTM栈 — Loki、Grafana、Tempo、VictoriaMetrics —
  是我所有项目的标配。但真正的教训来自于我为矿业运营
  构建的燃油异常检测系统：纯传感器数据无法捕捉盗油模式。
  是GPS移动遥测数据与燃油读数的结合才让异常变得可见。
  第一个月就发现了三起盗油事件，
  年燃油成本降低了8-12%。这里的启示是：
  可观测性不只是仪表盘 —
  而是知道哪些信号真正重要，并在本来没有设计要互相通信的
  各层之间进行关联分析。

- **为最坏情况而构建。**
  我经历过的最艰难的工程问题都有一个共同模式：
  系统在正常条件下运行得很好。
  然后，通往偏远矿山的VSAT链路降到了512kbps —
  或者一个自相交多边形悄无声息地破坏了所有下游空间查询 —
  或者处于信号盲区的现场工作人员需要离线同步但又不丢失贷款发放数据。
  在BTPN，我通过离线优先架构将数据丢失率从23%降到零。
  在Petrosea，我构建了每秒处理5万条空间事件、
  响应时间不到2秒的地理围栏越界检测系统。
  快乐路径工程很简单。边缘情况才是系统存在的意义所在。

- **AI辅助，而非AI依赖。**
  Claude Code、MCP服务器、语义搜索是力量倍增器 —
  我积极使用它们。但我仍然会审阅每一条diff，
  对每一次部署负责，为每一行上线的代码背书。
  杠杆可以转移，但责任不行。
  工具加速执行，但不能替代理解一个设计决策背后的原因。
  如果在事故发生时，晚上11点我无法向另一位工程师
  解释其中的权衡，那我就不应该把它上线。
